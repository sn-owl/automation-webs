# 아키텍처 — 개인화 입력과 범용 업무 처리

이 문서는 이 저장소가 무엇을 어떤 원칙으로 처리하는지 설명하는 설계 계약이다.
코드의 docstring이 이 문서의 장 번호(`docs/ARCHITECTURE.md §N`)를 참조한다.

## 1. 한 문장 정의

서로 다른 사용자와 플랫폼에서 업무를 수집하는 **개인화 입력 제품**과, 공통 입력을 받아 한 사용자 안에서도 다양한 도메인을 분류하고 요청된 패턴을 평가·제작·검증·등록·호출하는 **범용 처리 제품**을 만든다. 최초 수행 패턴은 Excel 데이터 정리와 읽기 전용 코드 분석이며 제품의 도메인 상한이 아니다.

무더위쉼터 HWPX→XLS는 이 계약에 들어가는 하나의 기존 사례다. 제품 정체성, 공통 taxonomy, 필수 첨부, 단계 순서, 출력 형식, 검증기의 전역 기준이 아니다.

## 2. 제품 정체성과 경계

### 2.1 제품 A — 개인화 입력·수집

사용자별 플랫폼, 인증·로그인 세션, 수집 범위·주기·cursor, 원본 필드 추출, 다운로드/첨부 보관, 플랫폼 식별자를 담당한다. 게시판·메시징·이메일·이슈·로컬 입력 등은 각각 연결 방식이 다를 수 있다.

수집기는 플랫폼별 원문을 공통 WorkItem 경계로 전달한다. 업무의 최종 도메인·담당·자동화 수준·선택 Recipe를 결정하거나 실행 권한을 부여하지 않는다. Source별 사전 분류 정보가 있으면 출처와 함께 관찰 데이터로 제공할 수 있으나 Core의 확정 판단으로 위장하지 않는다.

### 2.2 제품 B — 범용 분류·판정·프리셋 처리

공통 WorkItem과 명시적인 판단/권한 문맥을 받아 다도메인 직무·책임 분류, 사용자 요청 시 자동화 가능성 평가, 패턴 선언·시험·등록, 조건 매칭, 승인된 준비 수행과 결과 검증·알림을 담당한다.

**한 사용자·한 설치·한 수집 플랫폼 안에서도 여러 도메인을 처리한다.** 특정 회사의 팀 목록이나 특정 문서 양식을 지원 도메인의 닫힌 목록으로 만들지 않는다. 새 도메인을 인지·평가하는 능력과 그 도메인의 모든 작업을 즉시 실행할 수 있는 능력은 별개다.

### 2.3 개인화가 허용되는 것과 금지되는 것

| 구분 | 허용 | 금지 |
|---|---|---|
| 입력 연결 | 사용자별 connector·계정 참조·source 설정 | 하나의 플랫폼이 전체 제품의 입력 계약을 독점 |
| 사용자 문맥 | 담당 후보·선호·용어·권한·승인 정책을 명시적 데이터로 제공 | 사용자마다 분류기/평가기 코드를 복제하거나 도메인을 한 종류로 고정 |
| 프리셋 | 사용자별 등록 내용·접근 권한·활성 범위 | 프리셋 내용을 공통 엔진 상수로 승격 |
| 실행 능력 | 허용된 Capability와 검증된 Executor를 확장 | 미지원 도메인을 이해·평가 자체가 불가능한 것으로 취급 |
| 데이터 | 소유 범위별 원본·근거·승인·결과 격리 | 범용 처리라는 이유로 사용자 간 비공개 자료·학습 신호를 자동 공유 |

두 제품은 우선 논리적 경계다. 별도 저장소·서버·마이크로서비스·멀티테넌트 SaaS 구축을 이번 요구에서 추론하지 않는다. 같은 저장소/프로세스여도 계약과 책임은 구분한다.

## 3. 목표 사용자 경험

입력 사용자: 자신의 플랫폼을 연결하고 수집 상태·누락 자료·연결 장애를 확인한다. 다른 사용자에게 같은 플랫폼을 강요하지 않는다.

업무 사용자: 어떤 플랫폼으로 들어왔든 원문·근거·직무·책임·confidence·다음 행동을 일관된 방식으로 확인한다. 첨부가 없거나 새로운 도메인이라는 이유로 수집된 업무가 사라지지 않는다.

패턴 제작 사용자: 사례와 기대 결과, 인식 방식, 단계·매개변수·적용 조건·검증 기준을 정의하고 초안을 시험·수정·등록한다. 같은 지원 능력 안의 새 패턴은 소스 코드를 고치지 않고 만들 수 있어야 한다. 새로운 준비 능력이 필요하면 무엇이 부족한지와 승인된 개발 경로가 표시된다.

## 4. 핵심 불변조건

아래 INV 식별자는 코드와 테스트가 참조하는 불변조건이다. 어떤 기능도 이 조건을 깨면서 추가되지 않는다.

- **INV-01 입력 경계:** 플랫폼/사용자별 수집 차이는 공통 입력 계약 앞에서 흡수한다. Core가 브라우저 DOM·쿠키·특정 게시판 필드에 의존하지 않는다.
- **INV-02 다도메인:** 한 사용자 안의 다양한 업무를 같은 분류·평가 계약으로 처리한다. 도메인 명칭과 조직 담당 목록은 확장 가능한 데이터다.
- **INV-03 판단과 능력 분리:** 도메인 불명, 근거 부족, 실행 능력 부재, 권한 부재는 서로 다른 이유다. 실행기 부재만으로 업무를 이해 불가/영구 수동으로 단정하지 않는다.
- **INV-04 의미 일관성:** 업무 내용·근거·명시 정책이 같으면 수집 플랫폼/계정 이름만 바뀌어 분류·평가가 달라져서는 안 된다. 신뢰도·권한 등 실제 문맥 차이가 판단을 바꾸면 근거를 노출한다.
- **INV-05 선언의 효력:** 처리 단계·매개변수·출력·검증 선언은 실행 계획에서 소비된다. 저장만 되는 선언 필드는 지원 기능으로 표시하지 않는다.
- **INV-06 조합 검증:** 허용된 연산, 매개변수, 입출력 호환성과 부작용 경계를 검사한다. 전체 계획이 특정 예제의 고정 단계와 같은지를 지원 판정으로 삼지 않는다.
- **INV-07 권위:** Core가 상태·버전·승인·실행·기록의 권위를 갖는다. 모델·수집기·UI는 이를 우회하지 않는다. 분류 AI에는 로컬 마스킹 요약과 비식별 직무·책임 기준만 전달하며 첨부의 내용·존재·이름·형식·개수는 전달하지 않는다.
- **INV-08 실행 안전:** 사용자 codebase·로컬 DB·원본은 읽기 전용이며 새 파생 파일만 생성한다. scope·task revision·입력 digest·정의·능력·관련 정책에 유효한 승인, 승인 철회, 원격 쓰기 기본 금지, 중복 실행 방지, 사용자 데이터 격리를 유지한다.
- **INV-09 근거와 학습:** 판단·조건·실행·결과·교정 근거를 연결한다. 같은 패턴 3회부터 후보를 제안할 수 있지만 사람 승인 없이 자동 승격하지 않는다.
- **INV-10 완료 증거:** 새 ID·상태 전이·파일 존재·테스트 개수는 범용성 증거가 아니다. 선언 변화에 따른 결과 변화와 서로 다른 도메인/작업 계열을 확인한다.
- **INV-11 실패 정직성:** 불명·미지원·실패·인계 필요를 성공으로 표시하지 않는다. 모르는 형식도 원본과 처리 불가 이유를 보존한다.
- **INV-12 검토 게이트:** 코드 계약 변경 전 사용자가 현재 R2의 계약 버전과 구현 범위를 검토하고 승인해야 한다. 검토안 작성이나 문서 수정 요청을 구현 승인으로 해석하지 않는다.
- **INV-13 범위 보존:** 편리한 예제나 이미 있는 실행기를 이유로 합의 범위를 축소하지 않는다. 제품 방향을 좁히는 결정은 사용자에게 검토받는다.
- **INV-14 최소 구조:** 두 제품 경계를 구현하되, 필요 없는 배포 분리·범용 코드 실행기·Factory를 추가하지 않는다. 불필요한 플랫폼화를 피하는 것과 범용 처리 능력을 생략하는 것은 다르다.

## 5. 전체 처리 흐름

```text
수신 → 인식 → 직무·책임 분류 → 계획 → 승인된 준비 수행 → 검증·제출 알림
             분류: 기존 패턴의 일치/미일치와 다음 행동 확인
             별도 요청: 자동화 가능성 평가 → 패턴 온보딩
             제출: 시스템 준비 완료 / 전달 / 사용자 결정 / 실제 업무 완료 분리
```

프리셋 제작은 별도 사용자 흐름이며 같은 Core 계약을 사용한다.

```text
사례·기대 결과 → 단계·입출력·조건·검증 선언 → 초안
→ 능력/형식/권한 검사 → 격리 시험 → 내용 검증 → 사람 검토 → 활성 등록
→ 실제 업무 유입의 조건 선택 → 승인된 실행 → 피드백·새 버전
```

새로운 업무 도메인에는 기존 능력으로 조합 가능한 경로와 새 능력이 필요한 경로를 구분한다. 자동화할 가치가 없거나 정책상 금지된 경우에도 판단 근거와 사람의 처리 경로를 남긴다.

## 6. S1 — 개인화 수집

Source Adapter는 플랫폼 인증 참조, 수집 범위, cursor, 원문 식별·시각·첨부 수신과 재수집 처리를 담당한다. 원격 세션과 자격증명은 입력 제품의 로컬 연결 경계에 남긴다.

기존 Chrome/그누보드/eGov 어댑터는 재사용 가능한 현재 구현 사례다. 향후 Source를 추가할 때 Core 분류·평가·Recipe 의미를 수정해야 한다면 경계 위반이다. 실제 지원 플랫폼 수는 구현 증거로만 표시한다.

수집 결과에는 source 식별·소유 범위·원본 참조·무결성·수집 완료 여부가 필요하다. 플랫폼 완료 표시와 Core 업무 완료를 혼동하지 않는다.

## 7. S2 — 적재와 식별

원문·첨부는 불변으로 보존하고 정규화 결과·판정·준비 결과를 분리한다. 소유 범위·Connector·source·외부 ID가 업무를 식별하고 의미 있는 내용 digest가 revision을 구분한다. source 완료 감지는 새 revision이나 사용자 실제 완료가 아니다.

현재 파일 기반 저장을 우선 재사용한다. 두 제품이라는 이유만으로 DB 전환을 수행하지 않는다. 같은 업무의 재수집·입력 수정·재실행은 별도 개념이며 승인과 실행 키를 임의로 재사용하지 않는다.

운영 `runtime/`과 검증 `runtime/_sessions/<session-id>/`를 분리한다. 기존 runtime·WorkItem·이벤트·산출물을 병합/이동하려면 참조·사용 프로세스·해시·복구 계획을 확인하고 필요한 승인을 받는다.

## 8. S3 — 공통 내용 추출

플랫폼 외피 제거는 제품 A, 파일/내용 형식별 공통 파싱은 제품 B의 재사용 가능한 능력이다. HWPX·PDF·문자열·표·이미지·구조화 필드 등은 서로 다른 자료 표현이며 모든 업무가 HWPX 표를 가져야 하는 것은 아니다.

원본 보존, 크기·경로·압축 안전 검사, 추출 결과와 출처 연결, 지원/미지원/불명 상태 기록을 유지한다. 파싱 실패를 빈 성공으로 위장하지 않는다. 추출기 안에 조직 담당이나 특정 업무의 최종 자동화 판정을 넣지 않는다.

## 9. 공통 WorkItem 계약

제품 A는 제품 B가 이해할 수 있는 플랫폼 독립 입력을 제공한다. 논리 요소는 계약 버전, 소유/source 범위, 외부 식별·수신 시각, 원본·수정 식별, 제목/본문 또는 구조화 내용, 선택적 첨부와 원본 참조, provenance 및 마스킹 참조다.

첨부·작성자·URL은 모든 플랫폼에서 반드시 존재한다고 가정하지 않는다. 플랫폼 확장 필드는 이름공간과 출처를 가진 관찰 데이터로 보존한다. 확장 필드에 실행 명령이나 승인 효력을 부여하지 않는다.

구체 JSON 필드와 필수/선택 여부는 `schemas/`의 JSON Schema가 소유한다. 기존 기록의 의미를 조용히 바꾸거나 플랫폼별로 다른 분류 계약을 만들어서는 안 된다.

## 10. S4 — 범용 분류

질문은 **이 업무가 무엇을 요청하고 어떤 도메인·대상·행위·제약·담당 문맥을 갖는가**다. 도메인, 요청 행위, 대상/자료, 반복성 단서, 담당 후보, 불확실성과 근거를 공통 방식으로 표현한다.

도메인·업무 라벨·조직 담당은 확장 가능한 식별/용어 데이터다. `development/design` 또는 무더위쉼터 등 현재 사례의 닫힌 enum이 새로운 업무의 저장·판단을 막지 않아야 한다. 상태·위험 처리 방식 같은 제어값은 검증된 닫힌 계약으로 유지할 수 있다.

승인된 heuristic은 원래 방식으로 판단한다. AI 판단이 필요한 업무에서 비활성·호출 실패·응답 검증 실패는 구분된 이유의 `DO NOT + 사용자 검토`이며 임의 heuristic fallback을 쓰지 않는다. 새 라벨은 데이터이며 코드 실행이나 자동 정책 변경이 아니다. Source 이름만으로 도메인을 확정하지 않는다.

## 11. S5 — 요청 시 자동화 가능성 평가

분류와 자동화 가능성 평가는 분리한다. 일상 분류는 기존 승인 패턴과의 일치 여부를 확인할 수 있지만 새 자동화 가능성을 항상 계산하지 않는다. 사용자가 특정 업무나 반복 패턴의 온보딩을 요청할 때만 반복성·결정성·입력 충족·출력 검증 가능성·부작용·권한·필요 능력을 평가한다.

평가할 때는 **업무 성격상 준비를 자동화할 수 있는가**, **현재 설치된 능력으로 준비할 수 있는가**, **지금 이 입력과 권한으로 준비해도 되는가**를 분리한다. 등록 패턴 부재를 자동화 불가로, 익숙하지 않은 도메인을 수동 처리 확정으로 바꾸지 않는다.

개인화 정책은 권한·승인·담당·선호 등 명시적 문맥이다. 공통 평가 원리를 사용자별 코드나 고정 도메인 분기로 바꾸는 수단이 아니다. 추정 소요시간은 근거와 불확실성이 없으면 확정 수치로 쓰지 않는다.

## 12. 자동화 가능 수준

일상 분류의 최상위 결과는 `내 업무 / 다른 담당자 / 정보 부족`과 근거·confidence·다음 행동이다. `DO`는 계획·준비 후보이며 `DO NOT`은 자동 진행하지 않고 검토·인계·정보 보완으로 분기한다.

요청된 온보딩에서는 준비 가능성·현재 능력·현재 입력/권한을 분리한다. 과거 Manual/Assisted/Developable/Ready 표기를 일상 분류의 필수 축이나 제품 범위로 승계하지 않는다.

정보 부족과 판단 불명은 이유를 별도로 기록한다. 모델이 판단을 제안하더라도 실행 권한은 Core 정책과 사람에게 있다.

## 13. S6 — 패턴과 프리셋 축적

사례·판단 근거·사람 교정·실제 처리 절차·기대/실제 결과를 연결해 저장한다. 분류 교정, 적용 조건 교정, 입력 보완, 실행 결함, 결과 보정을 구분한다.

분류 조건은 Rule, 평가 조건은 Evaluation Rule, 선언 가능한 실행 절차는 Recipe/Preset, 추가 실행 능력은 Capability/Executor, 사람 절차는 Manual Template으로 이어진다. 모든 교정을 키워드 룰이나 Hermes Skill로 바꾸지 않는다.

후보→독립 사례/반례 검증→사람 검토→활성→필요 시 중지/새 버전을 유지한다. Rule 학습과 실행 절차 제작을 구분하고, 사용자 간 비공개 사례를 자동 합치지 않는다. 기존 `candidates/replay/promotion`은 실제 역할에 맞게 재사용한다.

## 14. S7 — 선언 제작과 실행

### S7-A 지원 능력으로 프리셋 제작

사용자는 입력 계약, 처리 단계와 매개변수, 단계 간 데이터 참조, 출력 계약, 적용/제외 조건, 결과 검증과 승인 범위를 선언한다. Core는 이를 허용된 Capability 집합에 대해 검증하고 실제 실행 계획으로 만든다.

지원 판정은 전체 절차가 `_RESTAREA_STEPS`와 같은지가 아니라, 단계별 연산/매개변수·입출력 호환성·부작용·검증 가능성을 기준으로 한다. 같은 지원 능력의 매핑·필터·출력 변경을 위해 사용자에게 소스 수정을 요구하지 않는다.

초안→격리 시험→내용 검증→사람 검토→활성 등록을 거친다. 시험과 운영은 같은 선언 의미/실행 경로를 사용하며, 시험도 승인·부작용 경계를 우회하지 않는다. 실행에 소비되지 않는 선언을 제작 기능으로 표시하지 않는다.

### S7-B 미지원 능력의 개발

필요한 연산이 없으면 능력 요구서에 입력·출력·권한·검증·실패 조건을 기록한다. 승인된 개발 에이전트가 구현·검토·통합한 뒤 허용 목록에 추가한다. 운영 Hermes가 본문이나 모델 출력의 명령/모듈을 직접 실행하지 않는다.

사내 비공개 코드·서버 설정·자격증명은 정책 경계를 넘지 않는다. 개발 에이전트의 실제 diff·적용·commit·push·배포는 제품의 준비 수행 범위가 아니며 개발 작업의 최신 승인 범위를 별도로 확인한다. 2026-09-09 구현 승인 사실이 이번 문서 한정 작업을 구현 작업으로 바꾸지는 않는다.

### S7-C 실제 업무의 준비 수행

WorkItem→분류→활성 패턴 조건 매칭→현재 정의/입력/능력/정책과 승인 확인→Core의 읽기·분석 또는 새 파생 파일 생성→선언 기반 결과 검증→알림·사람 인계·기록으로 이어진다. 기존 파일 변경, 운영 DB 쓰기, 외부 사이트 적용·업로드·배포는 수행하지 않는다.

## 15. S8 — 인간 확인과 승인

판단 제안의 수락, 프리셋 검토·활성화, 개별 실행 승인, 코드 계약 변경 승인은 서로 다른 승인이다. 하나로 다른 승인을 대체하지 않는다.

승인은 대상·범위·관련 버전/입력·행위자·근거에 연결한다. 입력·정의·능력 또는 승인에 영향을 주는 정책 변경, 이후 reject/modify/defer에 대해 이전 효력을 재검증한다. UI/CLI/모델 경로 모두 같은 Core 게이트를 거친다.

사용자는 원문과 근거, 자동 준비될 부분, 남은 사람 행동과 결과 검증을 확인한다. 외부 사이트 반영·업로드·배포는 Core 수행 범위 밖이며 사용자의 별도 실제 업무로 남긴다.

## 16. S9 — 근거와 결과 기록

소유/source 범위, 원본/정규화 참조·버전, 분류·평가와 불명 이유, 선택 후보/제외 근거, 프리셋·능력·정책 버전, 승인 참조, 실행 키, 산출물 해시, 검증 항목·결과, 사람 인계·교정을 연결한다.

분류 완료·도구 실행 성공·산출물 검증 통과·자동화 단위 완료·원 요청 전체 완료를 구분한다. 비밀번호·쿠키·키·불필요한 원문을 로그/공유 문서로 내보내지 않는다. 기존 기록을 새 의미로 소급하여 성공 처리하지 않는다.

## 17. 상태기계

업무 상태, 패턴 제작 상태, 준비 수행 상태, 알림 전달 상태와 사용자의 실제 업무 완료는 별도 계약이며 각각의 전이 권위는 Core다. 문서의 화살표가 자동 전이나 승인 생략을 뜻하지 않는다.

```text
업무: 수신 → 인식 → 분류 → 계획/검토 → 준비 대기/진행/완료/중단 → 사용자 실제 완료
패턴: 초안 → 시험 → 검증 → 검토 → 활성 → 중지/새 버전
준비: 요청 → 승인 확인 → 진행 → 결과 검증 → 준비 완료 / 중단·실패 격리
알림: 요청 → 채널별 시도 → 전달/실패 → 필요한 사용자 확인
```

플랫폼별 cursor·재수집과 업무 실행 idempotency를 분리한다. 원본/승인/실행 키를 삭제하거나 바꿔 중복 차단을 우회하지 않는다. 프로세스 중단을 성공으로 기록하지 않는다.

## 18. Hermes와 모델의 역할

모델은 다도메인 직무·책임 분류, 조건/절차 후보, 부족한 입력 질문과 요청된 패턴의 자동화 가능성 평가를 제안한다. 한 조직의 닫힌 팀/업무 enum에 맞추기 위해 새로운 도메인을 오분류하지 않는다.

모델 제안은 검증되는 데이터다. Core 상태·승인·등록 승격·실행 코드를 직접 소유하지 않는다. 분류 모델에는 로컬 규칙으로 만든 마스킹 업무 요약과 비식별 직무·책임 기준만 전달한다. 원문·마스킹된 전체 본문·첨부 정보·치환표·자격증명을 전달하지 않는다.

코드 분석의 전체 codebase 접근과 외부 AI 코드 접근은 프로젝트 등록 시 각각 명시적으로 선택한다. 이것이 분류 AI의 정보 경계를 넓히지는 않는다. `hermes/assessment-prompt.md`, `skills/web-maintenance-triage/`와 Validator는 프로그램 소비 자료이며 이번 문서 작업에서는 변경하지 않는다.

## 19. 두 제품과 Core·모델의 결합

```text
ConnectorProfile → 제품 A → 공통 WorkItem → 제품 B Core
                                           ├─ 규칙/모델 제안 검증
PolicyContext ──────────────────────────────┤
                                           ├─ 분류·평가·능력 판정
활성 Recipe / Capability Registry ───────────┤
                                           └─ 매칭·승인·실행·검증·기록
사용자 제작 UI/CLI → 같은 Core 정의/시험/등록 계약
```

특정 UI·모델·플랫폼이 제품 B의 유일 진입점이 아니다. 기존 Python CLI/모듈 구조를 우선 사용하고, 플랫폼 추가나 도메인 추가마다 처리 엔진을 fork하지 않는다.

## 20. 외부 모델·알림·스케줄링

Hermes Skill/API, 메시징 Adapter, cron은 교체 가능한 연동이다. 로그인과 메시지 전달 상태는 입력/운영 준비 상태이지 범용 분류 능력의 정의가 아니다.

실제 Chrome 접근·외부 전달·Windows 재부팅 검증과 로컬 계약 검증은 분리한다. 외부 환경이 없어도 공통 입력과 분류·제작 계약의 격리 검증은 가능해야 한다. 미실행된 운영 검증은 미검증으로 남긴다.

외부 채널은 명시적인 설정과 승인이 있을 때만 활성화한다. 저장소에 코드가 있다는 사실만으로 외부 발송이 켜지지 않는다.

## 21. ConnectorProfile과 PolicyContext

ConnectorProfile은 사용자별 연결·소유/source 범위·계정 참조·수집 설정·원본 필드 매핑을 담는다. 비밀값은 코드/공유 설정/모델 입력에 넣지 않는다.

PolicyContext는 같은 처리 엔진이 해석하는 권한·승인·담당 후보·용어/선호 등 명시적 데이터다. 도메인 하나만 처리하는 사용자별 엔진 설정이 아니다. 동일 업무에 다른 권한 정책이 적용되면 판단 근거와 실행 허용 차이를 설명한다.

이 둘은 제3의 제품이나 사용자별 코드베이스를 만들기 위한 개념이 아니다.

## 22. Rule·Preset·Recipe·Capability·Executor·Skill

| 개념 | 계약상 역할 |
|---|---|
| Rule / Evaluation Rule | 공통 의미의 분류·평가 조건과 근거 |
| Preset | 사용자가 관리하는 작업 정의·적용 조건·검증·활성 버전의 사용자 개념 |
| Recipe | Preset의 실행 가능한 선언 계약. 기존 registry를 발전시키며 별도 의미의 중복 실행 레지스트리를 만들지 않음 |
| Capability | 허용된 작업 단위의 ID·버전·매개변수·입출력·부작용·검증 능력 |
| Executor | Capability를 실제 수행하는 검토된 코드 |
| Hermes Skill | 모델이 따르는 제안/상호작용 절차. 실행 권한 자체가 아님 |
| Manual Template | 해당 작업에서 사람이 수행할 명시적 단계 |

무더위쉼터 프리셋은 특정 입력·매핑·출력·검증 값을 가진 사례다. 그 값이 공통 Capability의 고정 매개변수 전체가 되어서는 안 된다. 특수 실행기를 남겨도 공통 프리셋 제작·분류 계약을 그 특수 실행기로 제한하지 않는다.

## 23. 사용자 화면과 명령

입력 설정/준비 화면은 연결·수집·권한 문제를 보여준다. 업무 화면은 도메인·행위·근거·불명/부족한 능력·후보 프리셋·승인·결과를 보여준다. 제작 화면/명령은 입력·절차·조건·검증 선언, 초안 수정·시험·등록을 제공한다.

현재 특정 플랫폼 로그인이나 HWPX를 모든 사용자의 시작 조건으로 안내하지 않는다. 같은 기능의 UI와 CLI는 동일 Core 계약을 사용한다. 사용자가 소스 또는 registry JSON을 직접 편집하는 것을 제작 제품의 인수 경로로 삼지 않는다.

화면이 있어도 선언이 실행에 영향을 주지 않으면 실패다. CLI가 있어도 내부 상수와 정확히 같은 JSON만 입력하도록 요구하면 다양한 프리셋 제작을 충족하지 않는다.

## 24. 보안 경계

- 원본·자격증명·마스킹 치환표·정책상 금지된 사내 코드의 모델 전달 경계를 유지한다. 소유 범위 간 자료와 승인도 분리한다.
- 업무 본문·첨부·Source 메타데이터·모델 응답은 신뢰되지 않는 데이터다. 도구/명령/경로/정책 지시로 실행하지 않는다.
- 허용된 Capability/Executor와 검증된 매개변수만 실행한다. 유형 이름을 임의 import/쉘 명령으로 해석하지 않는다.
- 승인 전 부작용 실행 금지, 원격 쓰기 기본 금지, 코드 적용·commit·push·배포의 별도 승인 경계를 유지한다.
- 고정된 무더위쉼터 절차만 허용하는 것은 안전 불변조건이 아니다. 허용 능력 확장과 안전한 조합을 함께 검증한다.

## 25. 현재 구현 범위와 한계

이 저장소가 실제로 하는 일과 하지 않는 일을 분명히 해 둔다.

**구현되어 동작하는 것**

- 게시판 HTML → 공통 WorkItem 정규화, 중복·revision 식별, 첨부 참조 보존
- 규칙 기반 분류와 근거 기록, 정보 부족 시 보완 요청
- 요청된 패턴에 한정한 자동화 가능성 평가와 Recipe allow-list 검증
- 사람 승인 이후에만 실행되는 준비 수행(새 파생 파일 생성)과 결과 검증
- 결과 lifecycle(version/attempt), 실패 산출물 격리, replay 멱등성
- 이벤트 기록, 알림 큐, 읽기 전용 대시보드

**의도적으로 하지 않는 것**

- 기존 원본 파일 수정. 원본은 read-only이며 산출물은 항상 새 파일이다.
- 승인 없는 실행. 등록되지 않은 Recipe는 어떤 경로로도 실행되지 않는다.
- 모델이 스스로 실행을 결정하는 것. 외부 모델은 **제안만** 하고, 스키마 검증·allow-list·상태 전이·승인은 Core가 소유한다.
- 실제 업무 문서 포함. 공개 저장소의 fixture는 전부 비식별 placeholder다.

**검증 범위**

테스트는 합성 입력과 로컬 결정적 어댑터를 사용한다. 실제 로그인 세션 수집,
Windows Excel COM 실행, 외부 AI·메신저 발송은 각자의 환경 설정이 있어야 동작하며
자동 테스트 범위에 포함되지 않는다.
